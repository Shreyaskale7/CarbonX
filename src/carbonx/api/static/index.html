Calculating emissions is arithmetic. Proving them is not.

To check one figure, an auditor has to reconstruct this whole chain. CarbonX stores each link, so the chain can be read instead of rebuilt.

  1. Source document

    A bill or invoice, hashed with SHA-256 at upload.

  2. Activity

    The quantity and period. Corrections supersede; nothing is overwritten.

  3. Factor version

    The exact published row used, pinned for good.

  4. Calculation

    A typed program whose units must agree before it runs.

  5. Ledger entry

    The result, with a hash-chained audit event written by the database.

  6. Report

    Canonical output and its hash, reproducible as of its own time.

What the system guarantees

Reproducible reports
A report generated at one moment regenerates byte-identically later, whatever was revised or corrected in between. Tested with generated operation sequences.
Factors are superseded, never edited
A calculation keeps the factor row it used. New versions sit beside the old ones.
Audit trail in the database
Triggers write it, so it holds even when the application is wrong. The application runs as a role that cannot switch them off.
Units that must agree
kWh times tCO2 per MWh gives tonnes. kWh times kg per litre is rejected before anything is computed.
Tamper evidence
Documents are hashed and audit events are hash-chained. This shows tampering. It is not a blockchain.
No invented uncertainty
Ranges come from IPCC 2006 tables. Where nothing is published, the figure is a point estimate and says so.

What it is not

CarbonX does not verify emissions and does not issue assurance. Verification under CCTS is done by agencies accredited by BEE. This is a tool that puts the evidence in front of them.

The sample facility is synthetic. The bill reader was trained on synthetic bills, so every value it reads waits for a person to confirm it. The findings rest on one BEE document that still needs checking against the notified text.
